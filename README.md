# 운영비 정산 웹앱 (opex-app)

팀원 지출 입력 → PM 월 마감·상신 → 재무 승인/반려, 기존 상신 양식 엑셀 자동 출력.
기획·설계: [docs/PLAN.md](docs/PLAN.md) · 용어집: [docs/GLOSSARY.md](docs/GLOSSARY.md) · 연동: [docs/INTEGRATION.md](docs/INTEGRATION.md)

## 실행

```bash
pnpm install
pnpm db:setup     # 스키마 반영 + 데모 데이터 시드 (빈 DB에서만; 초기화는 pnpm db:reset — 기존 데이터는 prisma/backups/에 백업 후 삭제)
pnpm dev          # http://localhost:3000
```

데모 계정 (비밀번호 `password123`, 개발 모드 로그인 화면에 원클릭 버튼 있음)

| 역할 | 아이디(이메일, 도메인 @opex.local) |
| --- | --- |
| 프로젝트 PM | pm · pm2 · pm3(서브 프로젝트) |
| 팀원 | member1 ~ member5 |
| 재무 승인 | hq · finance2 |
| 시스템 관리자 | admin |

## 역할별 권한

| 역할 | 할 수 있는 일 |
| --- | --- |
| 팀원 | 지출 입력 — 결제방법 개인식법인카드 고정, PM이 노출한 항목만, 세부내역·대상인원·참석자 필수. 본인 내역·정산 조회 |
| 프로젝트 PM | 본인 지출 별도 입력(예산 항목 전체), 팀원 입력 취합 조회·수정, **PM 설정**(팀원 노출 항목), 프로젝트 운영비 조회, 월 마감·상신 |
| 재무 승인 | **전체 프로젝트 현황**(조직별 필터), **프로젝트 운영비(예산) 작성·수정**, **분류·항목·규정(한도) 관리**, 본사 집행 입력, 상신 승인/반려/승인 취소 |
| 시스템 관리자 | 조직도(임시)·사용자 계정(임시 비밀번호·잠금 해제·비활성화·CSV 일괄 등록)·프로젝트 관리, 접속·변경 기록 점검 |

분류·항목은 재무 승인 담당이 예산에 등록한 범위를 벗어날 수 없고, 분류는 항목 선택 시 자동 지정된다.

로그인은 아이디(회사 이메일 주소 전체) 또는 사번. 계정은 시스템 관리자가 임시 비밀번호를 발급하고, 첫 로그인 때 비밀번호를 바꾼다. 조직도·통합 로그인 연동 준비 사항은 [docs/INTEGRATION.md](docs/INTEGRATION.md).

## 프로젝트 구조·PM 지정

- **재무 승인 담당**이 프로젝트를 만들며 기간·PM·상위 프로젝트·항목 구성을 정한다. 항목은 프로젝트마다 따로 관리(공통 기본 항목 또는 다른 프로젝트에서 복사).
- **PM 지정**: 재무 승인·시스템 관리자가 프로젝트의 PM을 지정하면 팀원에게 PM 권한이 자동 부여되고, 어느 프로젝트에서도 PM이 아니게 되면 자동 회수된다(시스템 관리자가 직접 준 PM 권한은 유지).
- PM 권한이 있어도 **PM으로 지정되지 않은 프로젝트에서는 팀원**으로 동작한다.
- **서브 프로젝트**: 상위 PM은 하위 프로젝트의 PM·팀 내용을 조회 전용으로 보고, 대시보드·팀 현황·팀원별 정산에서 "하위 포함"으로 모두 취합한다. 하위 PM은 상위 프로젝트를 볼 수 없다.
- 데모: 플랫폼사업팀(PM 김하늘) ⟶ 모바일 앱 고도화(PM 서하준, pm3@opex.local)

## 조직도(OBS) · 프로젝트 체계도(EPS)

- **조직도**는 조직 아래 사람(OBS, Organizational Breakdown Structure), **프로젝트 체계도**는 조직 아래 프로젝트(EPS, Enterprise Project Structure)다. 모든 프로젝트는 반드시 하나의 조직에 속한다.
- **조직장**(부서별 지정)은 자기 조직과 하위 조직의 모든 프로젝트를 조회·취합한다(입력·마감은 각 프로젝트 PM). 데모: 사업본부 조직장 임도윤(head).
- 재무 승인·시스템 관리자는 프로젝트 체계도에서 조직을 골라 프로젝트를 만들고 다른 조직으로 옮긴다.
- 회사 조직 구조는 Soliday에서 가져온 부서(사람 제외)를 사용한다 — prisma/data/soliday-departments.json(커밋 제외)이 있으면 시드에 포함된다.

- 메뉴 **조직도**: 모든 임직원이 부서 트리·임직원(직위·권한·참여 프로젝트)을 조회. 시스템 관리자는 같은 화면에서 임직원 추가·수정·부서 이동·권한·임시 비밀번호·잠금 해제·비활성화(퇴사)와 부서 추가·수정을 한다.
- **Soliday 연동**: 마스터 관리 > 조직도 탭 — ① Soliday 화면에서 보내기(전송 링크·북마클릿, 10분 유효) ② API 토큰 ③ JSON 파일. 로컬(http://localhost)에서는 Chrome의 로컬 네트워크 접근 허용 창이 뜰 수 있으며, 클라우드(https) 배포 후 사용을 권장.

## 규정 점검

지출 저장 시 자동 점검하고, 걸리면 **소명 사유**를 입력해야 저장된다.

| 점검 | 기준 (재무 승인 담당이 항목별 설정) |
| --- | --- |
| 1인당 한도 | 금액 ÷ 대상인원 > 항목 1인당 한도 — **한도 금액(한도 × 인원)으로 정산**하고 초과분은 본인 부담. 세부내역 뒤에 `(결제금액:13,000원)`을 자동으로 붙인다 |
| 1건 한도 | 금액 > 항목 1건 한도 — 위와 같이 한도 금액으로 정산 (둘 다 있으면 작은 쪽) |
| 예산 잔액 초과 | 항목 잔액보다 큰 금액 (예산 강제 항목은 저장 차단) |
| 중복 의심 | 같은 결제자·날짜·금액 |

주말·심야 사용은 점검하지 않는다(2026-10-15 확정 — 긴급 장애 출근이 있음). 영수증 첨부는 범위에서 제외(2026-10-14 — 증빙은 법인카드 내역으로 갈음).
| 계정 확인 | 거래처 참석인데 복리후생비 계정 항목 |

- **출입증 1일 한도**: 출입증 회사 부담 항목(예: 야근식대)에 1인 하루 한도가 있으면 같은 사람·같은 날·같은 항목의 회사 부담(식당·카페 등 사용처가 달라도 합산)은 **한도까지만 회사 부담**이고 초과분은 본인 부담(급여 공제)이다. 화면 경고는 `⚠ 야근식대 1일 한도 12,000원 초과 (회사 부담 12,000원 · 본인 부담 5,000원)`. 배분은 `lib/pass-statement.ts`의 `companySplit` 한 곳에서 하고 PM·팀원 화면, 급여 공제 엑셀, 예산 집행, 상신 엑셀, 카드 입력의 잔액 계산이 모두 그 결과를 쓴다 (tests/limit-cap.test.ts).
- **출입증 월 확정**: 확정은 내역 상태만 CONFIRMED로 바꾸고 **줄은 바꾸지 않는다**. 확정된 내역에서 결정이 비어 있는 줄은 **본인 부담(급여 공제, 출처 "기본")으로 읽는다** — `lib/pass-statement.ts`의 `applyConfirmedDefaults`를 서버 로더·엑셀·API가 모두 거친다. 확정 취소하면 그 줄은 자동으로 다시 미결정이 된다. (예전처럼 확정 때 빈 줄을 전부 DEDUCT로 써 넣으면 줄이 많은 달에 운영 D1 바인딩 한도로 일부만 반영될 수 있어 바꿨다, 2026-10)

## 설계서 대비 변경 사항

- **인증**: NextAuth 대신 HMAC 서명 쿠키 + scrypt 비밀번호(`lib/session.ts`). SSO 도입 시 교체.
- **UI**: shadcn/ui 대신 Tailwind 공통 클래스(`app/globals.css`).
- **enum**: SQLite 호환을 위해 String 컬럼 + `lib/types.ts` 상수. PostgreSQL 전환 시 enum으로 변경 가능.
- **추가**: `Item.keywords`(세부내역 기반 항목 추천), `AuditLog`(변경 이력), 정산 검증 FALSE이면 마감 차단.
- **미구현**: Playwright E2E, 9단계 기존 엑셀 import 스크립트(원본 엑셀 파일 필요).

## 보안

- **세션**: HMAC 서명 쿠키 두 겹(HttpOnly·SameSite=Lax, 운영에서 Secure). 접근 토큰 `opex_session` **1시간**, 리프레시 토큰 `opex_refresh` **14일**(쓸 때마다 새로 발급되어 미뤄짐), 로그인 후 **30일 절대 만료**. 접근 토큰이 만료되면 미들웨어(화면)·API 클라이언트(401)·SessionKeeper(활동 중 20분마다)가 `/api/auth/refresh`로 조용히 재발급한다. 상수는 `lib/session.ts`(ACCESS_SEC·REFRESH_SEC·ABSOLUTE_SEC). 로그아웃·본인 비밀번호 변경·시스템 관리자 임시 비밀번호 발급·역할 변경·비활성화 시 `User.sessionVersion`이 올라가 그 사용자의 기존 세션이 모두 무효. 리프레시 토큰은 1회용(회전)으로 서버 기록(`RefreshToken`)과 대조하며, 이미 쓴 토큰이 30초 유예 뒤 다시 오면 복사된 것으로 보고 그 사용자의 세션을 전부 끊고 감사 로그에 남긴다 (`lib/refresh-rotation.ts`).
- **로그인 보호**: 시도 기록을 DB(`AuthFailure`)에 남겨 서버 인스턴스가 여럿이어도 함께 센다. 15분 안에 IP당 20회·IP+아이디 5회 실패면 429, 아이디 기준(모든 IP)으로는 10회부터 점진 지연·50회면 차단, 전체 1분 100회 이상이면 모든 시도 2초 지연. 시도는 비밀번호 검증 **전에** 기록해 동시에 보낸 요청으로 한도를 넘지 못한다. 없는 계정·틀린 비밀번호·잠김은 같은 문구로 응답하고(없는 계정에도 더미 해시 검증으로 응답 시간 균일), 실패 로그의 입력 아이디는 SHA-256 앞 12자리로만 남긴다. 비밀번호 변경의 현재 비밀번호 확인은 사용자당 15분 5회, PM의 팀원 임시 비밀번호 발급은 PM당 15분 10회로 제한(2026-10-20 5회→10회).
- **CSRF**: `/api/*` 변경 요청(POST·PUT·PATCH·DELETE)은 Origin(없으면 Referer) 호스트가 요청 Host와 같아야 한다(미들웨어). JSON API는 `Content-Type: application/json`만 받는다(415). 예외: 북마클릿 전송 `/api/directory/push`(10분·1회용 토큰).
- **보안 헤더**(`next.config.ts`): CSP(외부는 jsDelivr Pretendard 글꼴만), X-Frame-Options SAMEORIGIN, nosniff, Referrer-Policy, Permissions-Policy, 운영(https)에서 HSTS(includeSubDomains).
- **환경 변수**
  - `SESSION_SECRET` — 운영 필수, **32자 이상 임의 값** (`node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`). 없거나 짧거나 개발 기본값이면 운영 서버가 요청 처리 시 오류를 낸다. 바꾸면 모든 세션이 끊긴다.
  - `TRUST_PROXY=1` — 리버스 프록시(nginx 등) 뒤에서만 설정. 이때만 `X-Forwarded-For`·`X-Forwarded-Host`를 믿어 IP별 시도 제한·감사 로그 IP·Origin 검사에 사용한다. 미설정 시 감사 로그 IP는 "(미검증)"으로 표시되고 IP별 제한은 적용되지 않는다.
